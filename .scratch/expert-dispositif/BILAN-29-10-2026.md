## Mission 2 : faille du verrou de commit

**Faille confirmée sur le vrai journal.** Sa dernière entrée était le QC `VALIDÉ` du ticket `v2-collectif/23`, sans clôture : le hook autorisait le commit (code 0).

**Correction.**

- `cloture.py decision` écrit lui-même l'entrée `<id>/cloture`. Elle contient : ticket, base résolue, fichiers, empreinte, chemin et sha256 du rapport, id de l'entrée QC, verdict de l'expert, réserves acceptées. Le QC est lu dans le journal ; `--qc` doit lui correspondre.
- `cloture.py verrou` est appelé par `verrou-commit.ps1`, après les contrôles existants (`append.ps1 Validate` et `integrite.ps1`). Il recalcule tout au lieu de faire confiance à l'entrée.
- `integrite.ps1` surveille aussi `cloture.py` et `expert.md`. Les empreintes ont été mises à jour délibérément : avant la mise à jour, seuls les 3 fichiers modifiés étaient signalés.
- `append.ps1`, `detection-git.ps1`, le format du journal, `controle-qualite` et `valider-etape` n'ont pas changé. Le journal réel n'a pas changé non plus (sha256 `0109df94…`).

**Tests.** Banc `tests/test-verrou.sh`, dépôt jetable, scripts réels, hook réel : **36/36**. La raison de chaque refus a été relue. Un test (I27) bloquait pour une mauvaise raison ; il a été corrigé puis rejoué.

- Interruptions : après le QC (I1), après le rapport (I2), pendant l'écriture de la clôture (I3), nouvelle entrée après la clôture (I8, I9).
- Rapport absent ou modifié (I6, I7) ; code modifié après la revue (I4, I5, I35).
- Clôture ancienne forme ou forgée (I10, I18-I20) ; journal malformé, vidé, supprimé, ids dupliqués (I21-I24).
- Fichiers indexés non revus, ou revus mais non indexés (I25, I27, I28).
- Intégrité (I29-I31) ; chemins favorables (S0, I14, I26, I33).

**Vrai dépôt.** Après correction, le hook refuse le commit (« une entrée QC seule ne vaut pas clôture »). Une commande sans git passe toujours.

**Risques restants.**

1. **Conséquence voulue mais à confirmer** : tout commit exige maintenant une clôture de ticket. Le travail hors ticket (dont ces corrections) ne peut plus être commité par la voie normale.
2. `git commit -a` ou `git commit <chemin>` : d'autres fichiers modifiés peuvent partir dans le commit. Les fichiers revus restent protégés par l'empreinte.
3. Un commit lancé depuis un script n'est pas détecté (limite déjà connue).
4. Une falsification cohérente par la même main reste possible : il faut forger ensemble le journal, le rapport et `reserves_acceptees`.
5. Le rapport est lu dans le scratchpad de la session : changer de session oblige à refaire la clôture (refus par défaut).

**Recommandation : garder les deux agents séparés, sans fusion de responsabilités.** Leurs angles morts sont complémentaires.
